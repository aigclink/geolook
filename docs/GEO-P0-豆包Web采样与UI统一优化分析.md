# GEO 项目 P0 优化分析：豆包 Web 采样与 UI 全覆盖

> 文档日期：2026-08-12  
> 适用阶段：GeoLook MVP 及第一轮真实品牌验证  
> 结论：当前最高优先级不是继续增加诊断规则，而是补齐真实消费端采样，并把已有能力统一收敛到 UI 工作流，尤其是无站点项目。

## 1. 结论摘要

建议把以下两项列为同一阶段的 P0 工作包：

1. **豆包 Web 采样闭环**：支持豆包登录态、问题队列、人工确认提问、答案和引用提取、样本上传、人工复核及复测对比。自动跑队列只能作为显式 opt-in 的实验能力，默认保持人工确认。
2. **UI 全覆盖**：UI 成为默认入口，CLI 保留为脚本化和运维入口；两者调用同一套业务服务和状态模型。无站点项目从创建、材料导入、事实确认、问题库、采样、阵地诊断、内容审核到发布包和复测，都必须在 UI 中完成。

这两个 P0 直接决定 MVP 能否回答核心问题：真实用户在豆包等国内 AI 入口看到什么，以及一次优化实验能否由非开发人员完整执行。

## 2. 当前差距与证据

### 2.1 豆包 Web

当前已经具备可复用基础：

- `scripts/sample.py` 将方舟 API 注册为 `doubao`，网页/App 单独注册为 `doubao_app`，避免把 API 与消费端混算。
- `extension/sidepanel.js` 已通过 `doubao.com` 识别 `doubao_app`，支持载入队列、填入问题、提取答案、保存样本和上传看板。
- `extension/README.md` 已规定专用 Profile、人工确认、限速、验证码即停等采样纪律。
- Dashboard 已有人工采样表和 `/api/sample-import` 回灌接口。

仍有明显缺口：

- 豆包 Web 需要登录，当前文档仅标记“待登录后验证”，缺少真实站点回归记录和稳定选择器维护机制。
- 采样助手的自动识别依赖域名和页面 DOM；页面改版、重定向、登录墙或风控会导致填充/提取失败。
- Web 样本与 API 样本虽然有平台码区分，但 UI 需要更强地展示“豆包 Web / 豆包方舟 API / 豆包 App”的差异，防止用户汇总误读。
- 引用、页面 URL、截图、登录态、搜索开关等证据字段并非全部强制，人工样本质量仍依赖操作纪律。
- 缺少采样失败后的可恢复队列、失败原因分类和单题重采入口。

### 2.2 UI 全覆盖与无站点

当前已经具备：

- CLI `init --no-site --name ... --materials ...` 支持无官网品牌、电商商品、线下品牌和小程序项目。
- `crawl.py`、`audit.py`、`tasks.py` 对无站点有跳过技术体检、保留外部阵地和内容任务的分支。
- UI 页面在站点体检处能够显示“技术层不适用”，并引导用户查看阵地地图和问题库。
- UI 可以触发抓取、体检、采样、导出人工表、生成工单、生成资产、报告和验收等后台任务。

主要差距：

- UI 创建向导仍以“官网域名”为主要输入，不能自然创建“无站点 + 品牌名 + 材料文件/文本”的项目。
- 无站点项目缺少独立的材料管理、来源核验和品牌事实确认流程，用户仍需借助 CLI 或直接编辑文件。
- UI 的任务按钮本质上通过 `jobs.py` 拼接参数调用 `geo.py` 子进程；操作入口统一了外观，但输入、状态、错误、产物和续跑能力没有统一抽象。
- 页面仍要求用户理解项目 slug、文件路径、Markdown 采样表和命令行导入，和“非开发人员可完成闭环”的目标不一致。
- `sample-import`、发布结果回填、事实版本和备份恢复尚未形成完整 UI 流程。

## 3. P0-A：豆包 Web 采样方案

### 3.1 目标流程

```text
选择项目与“豆包 Web”
  → 选择采样环境（专用 Profile / 无痕）
  → UI 生成买家意图队列
  → 插件检测登录和页面状态
  → 填题（默认人工按回车）
  → 等待答案稳定
  → 提取答案、引用、页面 URL、截图
  → 单题保存 / 批量上传
  → 看板复核品牌、竞品、引用和疑似负面
  → 进入同口径复测
```

### 3.2 产品要求

- 平台标识固定为 `doubao_web`，与 `doubao`（方舟 API）和未来 `doubao_app` 分开统计；如暂时沿用旧码，必须在 UI 显示正式名称和终端。
- 进入采样前执行自检：当前域名、是否登录、是否处于专用 Profile/无痕、看板地址、项目市场和问题数。
- 默认人工模式：插件只填题和提取，发送动作由用户确认。自动队列必须二次确认、限题数、限间隔、检测验证码/风控并立即停止。
- 每条样本强制保存：问题 ID、完整回答、引用 URL、页面 URL、采样时间、模型/终端未知标记、联网/搜索状态、采样环境、截图或快照哈希、人工复核状态。
- 提取失败时保留当前题、错误分类和重试按钮，不丢失已保存样本；支持导出 Markdown 作为离线兜底。
- UI 以“证据等级 A：真实 Web 样本”展示，禁止和非联网 API 结果默认合并。

### 3.3 技术改造建议

1. **扩展适配层**：为豆包建立独立的输入框、发送状态、答案容器、引用选择器和风控关键词；通用启发式作为降级，不把单一 CSS 选择器当作唯一方案。
2. **采样状态机**：`ready → filled → submitted → generating → stable → extracted → saved → uploaded`，每次状态变更写入本地队列，支持刷新后恢复。
3. **证据附件**：插件截取当前答案区域或保存页面快照元数据；服务端限制大小、脱敏并关联 `sample_id`。
4. **服务端回灌幂等**：以 `project + platform + question_id + round + sample_environment` 生成业务键，重复上传更新同一条待复核记录，不产生重复样本。
5. **回归测试**：使用 `extension/test/fixture.html` 增加豆包类页面 fixture，覆盖登录提示、流式输出、引用链接、重定向和提取失败；真实豆包只做人工小样本验收，不进入自动化测试。

### 3.4 验收标准

- 新用户无需编辑 JSON 或运行 `sample-sheet/sample-import`，可从 UI 完成至少 10 道豆包 Web 买家意图题并上传。
- 100% 样本能回放完整回答；有引用时引用 URL 可点击，无引用明确显示“未发现引用”。
- 豆包 Web 与方舟 API 在引擎页、指标、报告和导出文件中均可区分。
- 断网、页面改版、验证码或看板不可用时，已保存样本不丢失，用户能看到可执行的恢复提示。
- 同一题重复上传不会重复计数，人工修正能在下一次重算后保留。

## 4. P0-B：UI 全覆盖，优先无站点模式

### 4.1 统一产品入口

UI 应成为“项目工作台”，CLI 只承担三类职责：批处理、外部调度、故障恢复。所有核心动作由同一业务服务提供：

```text
项目初始化 → 基础资料 → 问题库 → 采样 → 诊断 → 行动计划
→ 内容工作台 → 发布/人工发布包 → 验收复测 → 报告交付
```

每个动作统一返回 `job_id`、状态、日志、产物、错误码和下一步建议。UI 不再要求用户复制命令、填写文件路径或手工猜测下一步。

### 4.2 无站点 UI 流程

创建向导增加明确分支：

- **有官网**：品牌名、官网 URL、市场。
- **无官网**：品牌/商品名、市场、简介材料（粘贴文本或上传 Markdown/TXT）、可选外部店铺/社交链接。

无站点项目进入后应显示专属导航：

1. 材料与来源：原文、来源 URL、证据日期、确认状态。
2. 品牌事实：产品、场景、价格、边界、别名和禁止表述。
3. 问题库与采样：国内/海外平台、豆包 Web、人工证据等级。
4. 外部阵地：竞品引用域名、优先渠道、建设任务和已发布 URL。
5. 内容工作台：证据页、平台变体、审核和人工发布包。
6. 复测与交付：提及、描述准确性、引用来源和业务结果。

站点体检、robots、sitemap、llms.txt、JSON-LD 等模块在无站点模式下应隐藏或置为“不适用”，不能显示为失败分数；“自有站引用率”显示 `n/a`，外部阵地和内容指标继续计算。

### 4.3 UI 功能覆盖清单

- 项目创建、切换、复制、归档和删除保护。
- 材料上传/粘贴、来源维护、事实逐条确认和版本历史。
- 问题库增删改、分组、市场、稳定 ID、批量导入导出。
- API 采样、豆包 Web/其他 Web 人工采样队列、样本导入和复核。
- 站点诊断（有站点时）、外部阵地诊断（所有项目）。
- 工单生成、负责人/状态/风险/验收标准和失败重开。
- 内容大纲、AI 初稿、风险 lint、人工审核、平台变体。
- 官方发布、人工发布包生成、发布结果和 URL 回填。
- 复测、报告、交付包、备份恢复和运行历史。

### 4.4 统一交互与数据契约

建议先抽象稳定业务对象，再改 UI：`Project`、`Fact`、`Question`、`Sample`、`Task`、`ContentAsset`、`Publication`、`VerificationRun`。CLI 与 UI 共用同一 service 函数和 JSON schema，文件格式只作为持久化实现，不再作为用户界面契约。

任务状态至少统一为：`待执行`、`运行中`、`待人工`、`失败可重试`、`已完成`、`已取消`。所有长任务必须支持查看日志、取消、重试和从断点继续。

## 5. 实施顺序与范围控制

### P0-1（先做，约 1 周）

- UI 无站点创建向导和材料录入。
- UI 统一展示项目状态、下一步和产物。
- 豆包 Web 插件适配、平台码和证据字段确认。
- UI 内完成豆包队列、上传和样本复核。

### P0-2（随后，约 1～2 周）

- 采样状态机、断点恢复、幂等导入。
- 无站点事实/问题/阵地/内容/复测全流程。
- 人工发布包、发布结果回填和统一任务状态。
- fixture、单元测试和一次真实豆包小样本验收。

### 暂不纳入 P0

- 通过 Cookie 绕过平台限制的全自动发布。
- 一次性接入小红书、头条、百家号等所有国内平台。
- 多租户、计费、复杂 RAG、消息队列和数据库迁移。
- 把豆包 API 结果当作豆包 Web 结果的替代品。

## 6. 关键指标

- 豆包 Web 采样完成率、失败率、单题平均耗时。
- 有效 A 级样本占比、缺引用率、证据附件完整率。
- API 与 Web 的提及率/引用率偏差（分题、分轮次）。
- UI 完成率：不使用 CLI 完成初始化到复测的项目比例。
- 无站点流程完成率、材料到事实的确认耗时、外部阵地任务完成率。
- 任务失败可恢复率、重复上传重复计数率、发布结果回填率。

## 7. 最终判断

豆包 Web 采样解决的是“测不到真实入口”的可信度问题；UI 全覆盖解决的是“能力存在但用户无法稳定执行”的交付问题。无站点模式是 UI 统一的最重要试金石：它能迫使系统把品牌事实、外部阵地、内容和复测抽象成独立于官网的核心能力。

完成这两个 P0 后，再根据实际瓶颈决定是否引入 GEOFlow 或开发更多国内发布连接器。当前不建议先做大规模平台集成，因为那会把尚未验证的采样口径、内容审核和发布状态问题一起放大。
