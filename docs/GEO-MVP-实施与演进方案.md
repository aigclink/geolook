# 一站式 GEO 系统：MVP 实施与后续演进方案

> 文档版本：2026-08-07  
> 目标市场：中国  
> 当前阶段：非 SaaS、单机或单服务器快速验证  
> 最终决策：第一阶段使用 [GeoLook](https://github.com/aigclink/geolook) 完成 MVP；验证成功后，再根据实际需求选择 `GEORank + GEOFlow`、`GeoLook + GEOFlow`、继续使用 GeoLook，或自研必要模块。

## 1. 执行摘要

第一阶段不建设完整平台，也不同时集成多个项目。直接使用 GeoLook 跑通以下最小闭环：

```text
建立品牌事实卡和问题库
        ↓
采集国内 AI 的基线回答
        ↓
计算提及率、位次、引用和描述准确性
        ↓
诊断官网与外部信源缺口
        ↓
生成并发布一小批实验内容
        ↓
使用同一问题集复测并比较变化
```

选择 GeoLook 的核心原因不是它的功能最全，而是它最适合回答 MVP 阶段最重要的问题：

> 对特定品牌实施一轮可控的 GEO 优化后，国内 AI 产品中的品牌可见性和描述准确性是否发生了可复现的改善？

GeoLook 部署轻、数据本地化、支持 API 与人工采样混合、带原始回答和前后期验收，适合在较低投入下验证这个问题。它的品牌库和内容工作台足够支持小规模实验，但不适合长期的大批量 RAG 内容生产、多人审核和复杂多站点运营。

第二阶段不预设唯一技术路线，而是根据 MVP 暴露出的主要瓶颈做选择：

| MVP 后的主要需求 | 推荐路线 |
|---|---|
| 监测、诊断和少量内容已经够用 | 继续使用 GeoLook |
| 需要企业知识库、批量内容、审核和多站点发布 | `GeoLook + GEOFlow` |
| 需要公司目录、完整诊断工作台、多人产品化运营，同时需要内容工厂 | `GEORank + GEOFlow`，保留或重建监测层 |
| 只缺少知乎、公众号自动分发，且能接受浏览器自动化运维 | 评估 `GeoLook + gitgeo`；先以草稿模式做受控验证 |
| 只缺少小红书、头条、百家号等国内渠道 | GeoLook 或 GEOFlow + 自研发布连接器 |
| 要做 OEM/计费且能取得官方 Partner Key | 再评估 `deepseek-geo + geo-partner-backend` |

## 2. 项目目标与边界

### 2.1 MVP 目标

1. 为一个真实品牌建立可核验的品牌事实底座。
2. 建立一组覆盖推荐、比较、替代、价格、风险和使用场景的中文问题库。
3. 在重点国内 AI 平台建立可回放的回答基线。
4. 量化品牌提及、推荐位置、竞品占位、描述准确性和引用信源。
5. 找出官网技术、内容结构、问题覆盖和外部信源的主要缺口。
6. 生成并发布一批可控实验内容。
7. 使用同一口径复测，判断优化是否值得继续投入。

### 2.2 MVP 不做的事情

- 不做 SaaS、多租户、计费、套餐和客户自助注册。
- 不在第一阶段集成 GEORank、GEOFlow 和 GeoLook 的数据库。
- 不建设复杂的 Agent 编排平台。
- 不承诺某个 AI 平台一定引用某篇内容。
- 不用模型 API 的结果冒充真实 App 或网页端搜索结果。
- 不在未经审核的情况下自动发布 AI 生成内容。
- 不绕过登录、验证码、风控或平台服务条款进行批量采集和发布。

### 2.3 成功标准

MVP 的成功不是“生成了多少文章”，而是同时满足以下条件：

- 测量可复现：问题、平台、终端、模型、联网状态、时间和原始回答均有记录。
- 事实可追溯：对外使用的品牌事实均有来源，不确定信息明确标记为待确认。
- 执行可验收：官网资产、内容和分发任务有负责人、状态和验收条件。
- 结果可比较：基线期和复测期使用相同的问题集和统计口径。
- 决策可落地：能够明确判断继续轻量运营、引入 GEOFlow，还是停止投入。

## 3. 为什么第一阶段选择 GeoLook

### 3.1 与当前约束匹配

GeoLook 使用 Python 和本地文件，第三方依赖较少，可以直接通过 CLI 或本地 UI 运行。它不要求先部署 PostgreSQL、Redis、向量数据库、消息队列和完整账号体系。数据保存在 `work/` 目录，适合单人或小团队验证。

它已经覆盖 MVP 所需的大部分流程：

- 品牌事实卡、品牌别名、竞品和问题库。
- 官网抓取、可抓取性及内容结构检查。
- 国内和海外 AI 引擎采样。
- API 自动采样与人工采样表回灌。
- 原始回答回放、提及率、竞品对比和疑似负面提示。
- 内容 Brief、初稿、`llms.txt`、JSON-LD 和 HTML 片段。
- GitHub、WordPress 草稿、公众号草稿和 Webhook 发布能力。
- 周期复测、前后对比、任务验收和交付报告。

### 3.2 GeoLook 的关键边界

GeoLook 不是长期的一站式企业内容平台：

- 单机设计，没有完整的用户、角色和团队权限体系。
- 品牌事实库是轻量文件，不是完善的企业 RAG 知识库。
- 适合生成少量实验内容，不适合高并发、批量审核和大规模内容队列。
- 国内平台的真实消费端通常没有开放 API，仍需要人工采样。
- API 模型多数默认不联网，只能反映模型参数化知识，不能代表真实 AI 搜索结果。
- 多平台发布不等于知乎、小红书、百家号、头条等全部开箱即用。

这些边界在 MVP 阶段可以接受，因为当前目标是验证效果，不是提前建设长期平台。

## 5. GEORank、GEOFlow 与 GeoLook 的关系

### 5.1 GEORank 与 GEOFlow

二者由同一作者维护，产品理念互补，但当前未发现正式的代码级集成：

- 没有共享认证和用户体系。
- 没有共享品牌 ID 或数据库。
- 没有 GEORank 到 GEOFlow 的正式 API Client。
- 没有统一 Compose、事件协议或诊断结果导入流程。

适合的逻辑分工是：

```text
GEORank：企业资料、网站诊断、拓词和前置工作台
                         ↓
                 自建适配或人工导入
                         ↓
GEOFlow：知识库、RAG、内容生成、审核、CMS 和分发
```

因此，`GEORank + GEOFlow` 更像第二阶段的产品矩阵，不是第一阶段最低成本的组合。

### 5.2 GeoLook 与 GEOFlow

二者的分工更清晰：

```text
GeoLook：测量 → 诊断 → 形成实验任务 → 复测
GEOFlow：知识库 → 批量生成 → 审核 → 多站点发布
```

| 维度 | GeoLook | GEOFlow |
|---|---|---|
| 主要目标 | 可见性观测和实施验收 | 持续内容生产和运营 |
| 存储 | JSON、Markdown 等本地文件 | PostgreSQL、pgvector |
| 品牌数据 | 轻量事实卡 | 企业知识项目、来源、版本和 RAG |
| 内容 | Brief、少量初稿和部署资产 | 任务、批量生成、审核和 CMS |
| 发布 | 少量内置渠道和 Webhook | WordPress、Agent、HTTP API、多站点 |
| 协作 | 单机、小团队 | 用户、后台、队列和运营流程 |
| 最适合阶段 | MVP 和独立监测 | 验证成功后的规模化生产 |

对于本项目，`GeoLook + GEOFlow` 是当前最自然的长期候选组合。第一阶段先只用 GeoLook；确认需要内容工厂时再引入 GEOFlow，并保持 GeoLook 作为独立的外部评测层。

### 5.3 deepseek-geo 与 geo-partner-backend

`geo-partner-backend` 是真实后端，但不是完整 GEO 核心后端。其本地能力主要包括账号、JWT、品牌基本资料、余额、计费、支付、工单和管理后台。知识库、内容生成和发布等请求由代理路由转发到 `GEO_API_BASE`。

运行核心功能需要：

```env
GEO_API_BASE=https://your-geo-platform.example/api
GEO_PARTNER_KEY=<partner-key-issued-by-platform>
```

因此，该组合适合已经取得主平台 Partner Key、希望快速做 OEM 的团队；不适合要求核心 GEO 能力完全自主部署的 MVP。它还引入了外部平台连续性、价格、数据流向和接口变更风险。

### 5.4 gitgeo：应作为“受控发布自动化候选”重新评估

gitgeo 的 README 关于多平台发布并非空泛宣传。源码中已有发布层、文章状态和发布审计接口；目前注册的适配器为知乎、微信公众号草稿、DEV.to、Telegraph 和 DryRun。其中直接服务中国市场的实现是：

- 知乎：加载已保存的网页登录态，使用浏览器自动填写并点击发布。
- 微信公众号：加载网页登录态，使用浏览器自动填写并保存至草稿箱。

这使 gitgeo 成为“发布知乎和公众号”这个窄问题上的重要候选，原方案将它概括为轻量实验工具并不准确，已修正。

但它没有成为第一阶段主推荐，原因不是发布能力不足，而是与本项目的 MVP 优先级和风险约束不完全匹配：

| 判断维度 | gitgeo 的现状 | 对本项目的影响 |
|---|---|---|
| 部署 | PostgreSQL、ChromaDB、FastAPI、Dashboard、Scheduler、浏览器引擎；官方镜像约 4.3 GB | 明显重于 GeoLook，降低首次验证速度 |
| 中国渠道覆盖 | 已有知乎、公众号；未见小红书、头条、百家号等适配器 | “多平台”目前是 5 个适配器，不是中国主渠道的全面覆盖 |
| 自动发布机制 | 基于 CloakBrowser/Playwright，保存 Cookie/Storage State，以网页端自动化操作 | 账号风控、页面改版、登录态失效和平台条款风险高于官方 API |
| 发布确认 | 知乎适配器点击后直接返回成功，未校验最终发布状态；公众号仅保存草稿且状态查询返回 `unknown` | 不能仅以返回成功作为已发布和已收录证据 |
| 调度路径 | `auto_publish.py` 使用 `wechat`，注册适配器的键为 `wechat_mp` | 静态审阅发现键名不一致，默认调度可能无法调用公众号适配器；采用前必须修复并做实号验证 |
| AI 评测 | 4 个平台的桌面/移动网页探测，但问题模板固定且页面选择器依赖前端结构 | 不适合作为唯一评测基线；需保留 GeoLook 的问题库、原始样本和人工回灌纪律 |

此外，探测层读取了设备 profile，但当前调用路径没有将 viewport、UA 等 profile 参数传给浏览器 context；因此其“桌面 + 移动端”差异需要在真实环境中专门验证，不能直接把 README 的“8 个探测通道”视作 8 个独立真实终端样本。

推荐使用方式：先由 GeoLook 负责基线、选题、事实卡和复测；当验证表明知乎/公众号是关键分发渠道时，在隔离测试账号上把 gitgeo 作为发布执行器接入。第一轮只允许保存草稿，并校验文章标题、正文、素材、草稿 ID、外部 URL 和发布审计记录；稳定后再单篇、限速、人工审批地启用正式发布。

## 6. MVP 技术架构

```text
                    ┌──────────────────────────┐
                    │ 品牌官网及用户提供的资料 │
                    └────────────┬─────────────┘
                                 │ 抓取、人工核验
                                 ▼
┌────────────────────────────────────────────────────────┐
│ GeoLook                                                │
│ 品牌事实卡 │ 竞品 │ 问题库 │ 站点体检 │ 任务 │ 报告 │
└───────────┬──────────────────────┬─────────────────────┘
            │                      │
            │ API 采样             │ 人工采样表
            ▼                      ▼
  DeepSeek/Kimi/千问等 API   豆包/元宝/百度等 Web 或 App
            │                      │
            └──────────┬───────────┘
                       ▼
             原始回答、引用和指标快照
                       │
                       ▼
       官网资产 + 实验内容 + 外部平台人工分发
                       │
                       ▼
                  同口径周期复测
```

### 6.1 数据原则

- `facts.md` 是品牌事实的单一来源，所有内容生成必须引用其中已确认事实。
- 原始回答不可覆盖，每次采样生成独立快照。
- 平台、终端和联网状态分别记录，不跨口径合并。
- API Key 只存 `.env`，不进入文档、日志和版本库。
- 对模型生成的结构化结果做字段校验，对事实结论做人工审核。
- 发布操作保持人工确认，不对非幂等发布请求盲目重试。

## 7. MVP 实施计划

建议用 2～4 周完成一轮验证。实际周期主要由外部平台内容收录和 AI 索引更新速度决定，而不是开发速度。

### 阶段 0：部署与项目初始化

目标：在本机或单台 Linux 服务器启动 GeoLook。

```bash
cd geolook
pip3 install requests beautifulsoup4 lxml
python3 scripts/geo.py ui
```

默认访问地址为 `http://127.0.0.1:8765`。服务没有账号体系，不应直接暴露到公网。远程使用时优先通过 SSH 隧道访问；确需多人使用时增加反向代理和认证。

验收条件：

- UI 或 CLI 能正常启动。
- `work/` 数据目录可写且已纳入备份。
- `.env` 权限受控且未进入 Git。
- 选定一个真实品牌作为 MVP 对象。

### 阶段 1：建立品牌事实底座

录入和核验：

- 品牌规范名称、英文名、别名和常见错写。
- 工商主体和官网。
- 产品线、核心能力、目标客户和典型场景。
- 价格、资质、成立时间和关键数字。
- 3～6 个真实竞品及其别名。
- 禁止对外使用的表述和合规边界。

每条事实建议附带：来源 URL、证据日期、负责人和确认状态。官网抓取或模型推导的结果只能作为候选，不能自动升级为已确认事实。

验收条件：核心产品、卖点、价格和资质不存在“待确认”却被用于生成内容的情况。

### 阶段 2：建立问题库和采样矩阵

首期建议建立 30～100 个问题，分为：

- 推荐类：“国内适合中小企业的 XX 工具有哪些？”
- 比较类：“A 和 B 有什么区别，怎么选？”
- 替代类：“有哪些 A 的替代产品？”
- 价格类：“XX 一般怎么收费？”
- 风险类：“使用 XX 有哪些限制或风险？”
- 场景类：“制造业如何用 XX 解决 YY？”
- 品牌验证类：“某品牌是做什么的？”

品牌验证类因为问题中已经出现品牌名，必须与无提示的品类问题分开统计，否则会虚高提及率。

建议的中国市场采样分层：

| 层级 | 典型平台 | 方式 | 用途 |
|---|---|---|---|
| A：真实消费端 | 豆包、DeepSeek、元宝、百度 AI、千问、Kimi 的 Web/App | 人工或合规浏览器操作 | 最接近用户真实体验 |
| B：联网 API | 支持搜索和引用返回的原生 API | 自动采样 | 可重复、可批量的检索评测 |
| C：非联网 API | DeepSeek API、默认 Kimi 等 | 自动采样 | 测量模型参数化知识中的品牌认知 |

同一产品的 Web、App 和 API 必须独立记录。每个样本至少保存：

- 问题 ID 和原文。
- 平台、终端、模型及版本。
- 是否联网、是否强制搜索。
- 采样时间。
- 完整回答原文。
- 引用 URL 或截图。
- 品牌、竞品命中结果。
- 人工复核状态。

预算允许时，每个核心问题可重复采样 2～3 次。不要用单次回答判断趋势。

### 阶段 3：生成基线报告

基线至少统计：

| 指标 | 定义 |
|---|---|
| 无提示提及率 | 未在问题中点名品牌时，回答包含品牌的样本比例 |
| 首位率/Top3 率 | 品牌出现在推荐列表第一位或前三位的比例 |
| 竞品占位率 | 主要竞品在相同问题中的出现比例 |
| 描述准确率 | AI 对品牌品类、能力、价格和边界描述正确的比例 |
| 引用覆盖率 | 回答中引用品牌官网或目标外部信源的比例 |
| 负面/风险线索率 | 出现疑似负面、过时或张冠李戴描述的比例 |

总分只能用于概览，所有评分必须可以下钻到平台、问题和原始回答。不能用一个综合分掩盖平台差异。

### 阶段 4：执行小规模内容实验

首轮不追求数量，建议选择 5～15 个高价值问题，每个问题制作一个可独立引用的证据页或内容单元。内容至少包含：

- 一句明确的定义。
- 带日期、单位和来源的数字事实。
- 同口径比较表。
- 可执行步骤。
- 适用与不适用场景。
- 可核验的外部引用。

官网侧优先处理：

- `robots.txt`、`sitemap.xml` 和静态 HTML 可抓取性。
- SPA 空壳页和正文不可见问题。
- 品牌定义块、产品页和 FAQ。
- Organization、Product、Article、FAQ 等适用的 JSON-LD。
- `llms.txt` 可作为辅助资产，但不应将其视为收录保证。

外部信源侧根据本行业真实采样中的引用域名决定优先级，不机械照搬全行业榜单。中国市场通常还需要考虑百度、字节、腾讯和阿里各自生态。

所有 AI 初稿必须经过：

1. 品牌事实核对。
2. 数字和引用链接核对。
3. 广告法、版权、隐私和行业合规检查。
4. 重复内容和平台规则检查。
5. 人工发布确认。

### 阶段 5：复测和决策

内容被收录并经过合理观察窗口后，使用完全相同的问题集和口径复测。报告应展示：

- 按平台和终端拆分的前后变化。
- 每个问题的原始回答差异。
- 竞品同期变化。
- 新增引用来源。
- 官网改动、内容发布时间和外部事件时间线。

只有存在基线窗口、观察窗口、对照问题和竞品对照时，才可以提高归因置信度。否则应表述为“与本轮优化观察相关”，不能直接宣称因果。

## 8. MVP 后的路线决策

### 路线 A：继续使用 GeoLook

选择条件：

- 品牌数量少。
- 单人或小团队运营。
- 每月只生产少量内容。
- 主要需求仍是诊断、监测、交付和复测。

需要自研的内容通常只有少量平台连接器和报表定制。这是成本最低的路线。

### 路线 B：GeoLook + GEOFlow

选择条件：

- GeoLook 已证明选题和内容实验有效。
- 需要处理较多企业资料和知识来源。
- 需要 RAG、批量生成、审核、任务队列和多站点内容运营。
- 仍希望保留独立于内容生产系统的评测层。

推荐职责：

| 系统 | 职责 |
|---|---|
| GeoLook | 问题库、基线采样、外部可见性、竞品对比和复测 |
| GEOFlow | 企业知识库、检索、批量内容、审核、CMS 和发布任务 |

第一版集成应采用“人工导入优先”：GeoLook 导出成功选题和事实要求，人工导入 GEOFlow；GEOFlow 发布后，把 URL、平台和日期回填 GeoLook。只有流程稳定后才开发 API 适配。

建议的最小交换字段：

```json
{
  "brand_key": "stable-brand-key",
  "question_id": "q001",
  "question": "目标问题",
  "market": "cn",
  "content_type": "comparison",
  "required_facts": ["fact-001", "fact-002"],
  "target_channels": ["official_site", "wechat"],
  "published_urls": [],
  "published_at": null
}
```

不要使用两个系统的自增数据库 ID 作为跨系统主键，应创建稳定的业务键。

### 路线 C：GEORank + GEOFlow

选择条件：

- 要做多人使用的完整 GEO 产品或内部平台。
- GEORank 的公司目录、问答、拓词和诊断工作台具有明确价值。
- GEOFlow 的知识库和内容工厂也不可缺少。
- 团队能承担两个复杂系统的部署和适配。

这条路线需要自行建设：

- 单点登录或统一认证。
- 品牌、企业和项目 ID 映射。
- 诊断结果到内容任务的转换。
- 统一模型供应商和密钥管理。
- 发布结果回写和评测闭环。
- 统一日志、告警、备份和权限。

由于 GEORank 与 GEOFlow 当前没有开箱即用集成，这条路线不应在 MVP 之前启动。

如果停用 GeoLook，还必须确认 GEORank/GEOFlow 是否已经覆盖所需的国内平台、终端、原始回答回放和前后期可重复评测；否则应保留 GeoLook，或单独建设评测服务。

### 路线 D：保留 GeoLook，选用 gitgeo 或自研发布模块

如果 MVP 证明真正的瓶颈只是国内发布渠道，且目标集中在知乎、公众号，可先评估将 gitgeo 作为受控发布执行器；它能够节省从零实现浏览器发布适配器的工作量，但必须先修复和验证适配器、密钥、Cookie、草稿状态与失败恢复流程。

如果渠道范围包含小红书、头条、百家号或其他未实现平台，则保留 GeoLook，同时开发：

- 微信公众号草稿/发布连接器。
- 知乎机构号发布辅助。
- 头条号、百家号或自有站点连接器。
- 小红书人工审核和发布工作台。
- 发布状态、失败原因和内容 URL 回写。

连接器必须提供超时、限流、幂等键、失败重试上限、人工确认和审计日志。遇到验证码、登录风控或平台禁止自动化时，应降级为“生成发布包 + 人工发布”，不要绕过平台限制。

## 9. 需要自行完成的工作

无论采用哪个开源组合，以下内容都不能完全依赖项目自动完成。

### 9.1 业务和数据

- 确定目标品牌、品类、核心场景和竞品。
- 核验品牌事实、证据来源和禁止表述。
- 设计符合中国用户表达习惯的问题库。
- 选择真正影响业务的 AI 平台和终端。
- 确定提及、排名、引用和准确性的统计口径。

### 9.2 内容和分发

- 审核模型初稿中的事实、引用和合规风险。
- 将同一事实改写为官网、公众号、知乎和其他平台适合的版本。
- 建设外部可信信源，而不只优化官网。
- 处理国内平台账号、审核、资质和发布限制。
- 记录每篇内容的发布时间、平台、URL 和状态。

### 9.3 工程和运维

- 密钥、账号和发布凭证管理。
- 数据备份和恢复验证。
- 采样失败、限流、超时和费用监控。
- API 模型、联网能力或搜索插件变更后的基线重置。
- 第二阶段系统间的数据契约和 ID 映射。
- 对外访问时的认证、权限、TLS 和日志脱敏。

## 10. 主要风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| API 结果不等于 Web/App | 指标与真实用户体验偏离 | 平台、终端、API 分开采样；关键平台保留人工真实样本 |
| AI 回答随机波动 | 单期涨跌被误判为效果 | 固定问题和模型；重复采样；至少观察两期同向变化 |
| 平台模型或搜索能力变化 | 历史指标失去可比性 | 保存模型、联网状态和时间；重大变化时重设基线 |
| 内容收录和索引滞后 | 过早复测得到假阴性 | 记录发布和收录时间；设置合理观察窗口 |
| 无法证明因果 | 错误评价 GEO 投入 | 使用对照问题、竞品对照和事件时间线；谨慎表述归因 |
| 模型编造品牌事实 | 发布错误内容、损害品牌 | 品牌事实白名单、来源字段、人工审核和生成后校验 |
| 提示注入和恶意网页内容 | 污染 RAG 或生成结果 | 把外部内容视为不可信输入；隔离指令与资料；限制工具权限 |
| 国内平台封闭生态 | 官网内容难以获得引用 | 按真实引用域名建设平台生态和外部信源 |
| 自动发布触发风控 | 账号受限或内容重复 | 人工确认、限速、草稿优先；不绕过验证码和平台限制 |
| 广告法、版权和行业监管 | 删除、处罚或法律责任 | 发布前合规审核；保留来源和授权记录 |
| 开源许可证不明确 | 商用和二次开发风险 | 使用前核对仓库 LICENSE、依赖许可证和素材授权 |
| 小型项目停止维护 | 安全和兼容问题积累 | 固定版本、保留 fork、建立最小回归测试和替换方案 |
| 多项目集成数据不一致 | 品牌事实冲突、结果无法追踪 | 统一业务键、事实版本和数据契约；明确主数据来源 |
| 凭证和客户资料泄漏 | 账号、费用和商业数据损失 | `.env` 不入库、最小权限、日志脱敏、目录权限和密钥轮换 |
| API 成本失控 | MVP 预算超支 | 限制问题数、平台数、重复次数、并发和每期预算 |
| 只优化提及率 | AI 提到了品牌但描述错误 | 同时衡量准确率、引用质量、位次和风险描述 |

## 11. 推荐的阶段性决策门槛

完成首轮复测后召开一次技术与业务评审，并回答以下问题：

1. 是否至少有一个重点平台出现持续的正向变化？
2. 描述准确率是否改善，而不仅仅是品牌名出现更多？
3. 哪类内容和信源与变化的相关性最高？
4. 当前瓶颈是采样、品牌数据、内容产能、审核还是发布？
5. 每月预计生产多少内容、管理多少品牌和发布到多少站点？
6. 是否出现多人权限、队列、版本和审核需求？

据此决策：

```text
没有可信改善
  └─ 调整问题、事实、渠道或停止扩大投入

有效且当前产能足够
  └─ 继续 GeoLook

有效但知识库/内容产能不足
  └─ GeoLook + GEOFlow

有效且要做完整多人产品
  └─ 评估 GEORank + GEOFlow，并保留独立评测层

有效但只缺国内渠道
  └─ 保留现有核心，自研少量发布连接器
```

## 12. 建议的最终交付物

MVP 结束时至少保留：

- 经人工确认的品牌事实卡。
- 带分组、市场和稳定 ID 的问题库。
- 每个平台和终端的原始基线回答。
- 基线指标和口径说明。
- 官网诊断与修复清单。
- 内容选题、初稿、终稿和证据来源。
- 发布平台、URL、日期和收录状态。
- 同口径复测原始回答与对比报告。
- 风险、失败样本和待解决问题清单。
- 第二阶段选型决策记录。

这些数据应保持可导出，不依赖某个 UI 才能读取，以便后续迁移到 GEOFlow、GEORank 或自研系统。

## 13. 最终结论

本项目第一阶段确定使用 GeoLook 做 MVP，不做多项目代码级集成。它负责建立品牌事实、问题库、国内 AI 可见性基线、网站诊断、轻量内容实验和前后期复测。

MVP 的判断重点是“是否获得可复现的业务信号”，而不是“是否搭出了功能最多的平台”。验证成功后：

- 需要规模化知识库、内容生成、审核和多站点发布时，优先选择 `GeoLook + GEOFlow`。
- 需要公司目录、完整工作台、多人协作和产品化时，再评估 `GEORank + GEOFlow`，同时补齐独立监测能力。
- 需求仍然轻量时继续使用 GeoLook。
- 只缺少国内平台发布时，开发少量合规连接器，不引入不必要的整套平台。
- `deepseek-geo + geo-partner-backend` 仅在取得 Partner Key、接受外部主平台依赖并确有 OEM 需求时重新评估。

这个顺序把最不可确定的部分，也就是 GEO 优化是否对目标品牌和目标平台有效，放在最先验证；把数据库、RAG、队列、账号体系和复杂集成推迟到需求已经被证明之后。
